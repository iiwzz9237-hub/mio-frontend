# MIO — فرانت‌اند مینی‌اپ

فایل اصلی **index.html** است. HTML، CSS، هشت سفینه، Canvas، صداساز و تمام JavaScript داخل همین فایل قرار دارند. پروژه به ابزار build نیاز ندارد. فایل‌های package.json، package-lock.json و پوشهٔ tests فقط برای آزمون توسعه هستند.

این تحویل فقط فرانت‌اند است. هیچ سرور بازی، دیتابیس، ربات، Telethon، parser انتقال یا اعتباردهی بانکی ایجاد نشده است.

## وضعیت فعلی

- آدرس بک‌اند عمداً خالی است. برنامه «در انتظار اتصال به سرور» نشان می‌دهد.
- نام و عکس، موجودی، کارت، بازیکنان و نتایج از خود برنامه تولید نمی‌شوند. مقدار نامشخص با «—» نمایش داده می‌شود.
- ثبت شرط، برداشت، ثبت کارت و تأیید مالکیت تا اتصال معتبر غیرفعال‌اند.
- مشاهدهٔ صفحه اصلی، فرم کارت، فهرست بازی‌ها، صحنهٔ موشک، راهنما و کپی شماره کارت بدون بک‌اند ممکن است.
- وقتی سرور کاربر بدون کارت تأییدشده برگرداند، ورود به صفحات دیگر تا تأیید کارت مسدود می‌شود.
- کارت شارژ ثابت **232491826963** است. کپی شماره کارت به معنی انجام انتقال نیست.
- سفینهٔ ساکن در حالت قطع ارتباط و موشک روی کارت بازی فقط عناصر بصری‌اند؛ هیچ دور آزمایشی یا ضریب تصادفی در رابط اجرا نمی‌شود.

## استفاده

برای مشاهدهٔ آفلاین، index.html را در مرورگر باز کنید. برای استفادهٔ واقعی در Telegram Mini App، همین فایل باید در یک میزبان HTTPS قرار بگیرد و آدرس آن برای مینی‌اپ تنظیم شود. کپی خودکار در مرورگرهای دارای Clipboard API از HTTPS استفاده می‌کند و fallback نیز دارد.

هیچ secret یا متغیر محیطی برای خود این فایل لازم نیست. هنگام آماده‌شدن بک‌اند، فقط تنظیمات عمومی **MIO_CONFIG** در ابتدای اولین script را ویرایش کنید:

| تنظیم | مقدار و کاربرد |
| --- | --- |
| apiBase | خالی یعنی بدون بک‌اند؛ برای اتصال، آدرس HTTPS واقعی سرویس را بنویسید |
| socketUrl | خالی یعنی همان میزبان apiBase؛ در غیر این صورت آدرس سرویس Socket.IO |
| socketPath | مسیر اتصال؛ پیش‌فرض /socket.io |
| socketClientPath | مسیر کتابخانه کلاینت؛ پیش‌فرض /socket.io/socket.io.js |
| requestTimeoutMs | پیش‌فرض 12000 میلی‌ثانیه |
| staleAfterMs | پیش‌فرض 5000 میلی‌ثانیه |
| minimumStake | مقدار قراردادی ثابت "2000000"؛ همین حد در validator هم اعمال می‌شود |
| depositCard | شماره ثابت "232491826963" |

apiBase شامل /api انتهایی نباشد، چون مسیرهای زیر خودشان با /api شروع می‌شوند. مسیر client باید توسط همان سرویس Socket.IO ارائه شود؛ فایل HTML در حالت بدون تنظیم سرور اصلاً آن را بارگذاری نمی‌کند. HTTP صرفاً برای localhost توسعه پذیرفته می‌شود.

SDK رسمی Telegram از https://telegram.org/js/telegram-web-app.js بارگذاری می‌شود. در صورت عدم دسترسی، صفحات آفلاین همچنان کار می‌کنند. احراز هویت از Telegram.WebApp.initData انجام می‌شود؛ برنامه برای احراز هویت یا عکس و نام حساب به initDataUnsafe اعتماد نمی‌کند.

در میزبانی جداگانه، بک‌اند باید Origin دقیق مینی‌اپ را برای CORS بپذیرد و هدرهای Authorization، Content-Type و Idempotency-Key را مجاز کند. Redirect برای API پذیرفته نمی‌شود. کوکی ارسال نمی‌شود.

## مرزهای اتصال

سه بخش در فایل با توضیح مشخص جدا شده‌اند:

1. MIOCore: قالب‌بندی فارسی، محاسبات صحیح با BigInt، اعتبارسنجی پاسخ و کنترل‌های ورودی.
2. MioAPI و MioRealtime: تنها محل ارتباط HTTP و Socket.IO.
3. رابط و SpaceScene / Synth: نمایش وضعیت و جلوه‌های کد اصلی.

قرارداد زیر **قرارداد پیشنهادی برای بک‌اند آینده** است، نه ادعای سازگاری تأییدشده با یک بک‌اند موجود. در صورت تفاوت API واقعی، آداپترها و validatorها باید با آن هماهنگ شوند. هیچ تست انتهابه‌انتها با بانک میویی یا سرور واقعی انجام نشده است.

## قرارداد HTTP

همهٔ پاسخ‌های موفق JSON هستند. پاسخ خطا باید کد HTTP مناسب و بدنهٔ { "code": "ERROR_CODE" } داشته باشد. متن خام خطای سرور مستقیماً در HTML درج نمی‌شود.

| روش و مسیر | ورودی | پاسخ موفق |
| --- | --- | --- |
| POST /api/session | { initData: string } | { accessToken: string, profile: Profile } |
| GET /api/me | بدون بدنه | Profile |
| POST /api/cards | { number: string } | Profile پس از ثبت درخواست؛ نه تأیید خودکار |
| POST /api/cards/verify | { challengeId: string, code: string } | Profile جدید |
| GET /api/crash/snapshot | بدون بدنه | Snapshot کامل |
| GET /api/crash/stats | بدون بدنه | Stats |
| POST /api/crash/bets | { roundId: string, stake: string } | { accepted: true } فقط پس از ثبت پایدار |
| POST /api/crash/cashouts | { roundId: string, betId: string } | { accepted: true } فقط پس از ثبت پایدار |

همهٔ درخواست‌ها به جز /api/session هدر Authorization: Bearer به همراه accessToken دارند. توکن فقط در حافظه می‌ماند؛ نه در URL و نه در localStorage.

عملیات POST کارت، شرط و برداشت Idempotency-Key می‌فرستند. سرور باید کلید را به کاربر، نوع عملیات و بدنهٔ درخواست مقید کند، نتیجه را پایدار نگه دارد و هم‌زمانی و تکرار را خودش حل کند. توکن یا کلید درخواست، شماره کارت یا مالکیت را در مرورگر معتبر نمی‌کند.

خطاهای شناخته‌شده: AUTH_REQUIRED، AUTH_EXPIRED، INIT_DATA_INVALID، INIT_DATA_EXPIRED، INSUFFICIENT_BALANCE، MIN_STAKE، BETTING_CLOSED، ALREADY_BET، ALREADY_CASHED_OUT، ROUND_CRASHED، CARD_UNVERIFIED، CARD_IN_USE، INVALID_CARD، VERIFICATION_UNAVAILABLE، INVALID_CODE، RATE_LIMITED.

## انواع داده

تعریف‌ها در این بخش مستندات قراردادند. دادهٔ نمونهٔ حساب یا بازی در برنامه قرار ندارد.

### قواعد مشترک

- مبلغ‌ها **رشتهٔ دهدهی صحیح و نامنفی** از میو پوینت هستند؛ بدون جداکننده، علامت، اعشار یا نماد علمی. حداکثر ۳۰ رقم. مقدار صفر "0" است؛ صفر اضافی در ابتدا پذیرفته نمی‌شود.
- شرط باید مثبت، حداقل "2000000" و حداکثر برابر موجودی باشد. سرور باید سقف عملیاتی خود را هم اعمال کند.
- ضریب بر حسب صدم و به شکل integer است: 250 به معنی 2.50× است. قرارداد فعلی بازهٔ 100 تا 10000 را مطابق سقف کد اصلی می‌پذیرد.
- مبلغ دریافتی از سرور باید برابر floor(stake × cashoutCents / 100) باشد. فقط پوینت کامل در این نسخه پشتیبانی می‌شود.
- revision یک integer ایمن و نامنفی است. revision موجودی و پروفایل مستقل‌اند. revision دورها باید در سمت سرور، حتی پس از ری‌استارت، ترتیب پایدار داشته باشد.
- id رشتهٔ ۱ تا ۱۰۰ کاراکتر از حروف انگلیسی، عدد، _ یا - است. UUID و Telegram ID رشته‌ای با این قالب سازگارند.
- زمان‌ها Unix milliseconds هستند. elapsedMs مدت پرواز بر حسب میلی‌ثانیه است.
- URL عکس باید HTTPS باشد یا null/رشتهٔ خالی. عکس از پاسخ معتبر بک‌اند خوانده می‌شود؛ در نبود آن آیکون عمومی نمایش داده می‌شود.
- فیلدهای nullable باید صریحاً null باشند؛ حذف فیلدهای الزامی پاسخ را نامعتبر می‌کند.

### Card

| فیلد | نوع |
| --- | --- |
| number | رشتهٔ ۱۲ رقمی بدون فاصله |

قالب ۱۲ رقمی از شمارهٔ مقصد داده‌شده استنباط شده است. اعتبارسنجی محلی فقط ساختاری است و اعداد تکراری مانند ۱۲ صفر را رد می‌کند؛ checksum یا قواعد واقعی بانک اعلام نشده‌اند. اعتبار نهایی و مالکیت باید در سرور بررسی شوند. اگر قالب واقعی بانک متفاوت است، validCardNumber و محدودیت فرم باید با مستند بانک تطبیق داده شوند.

### Profile

| فیلد | نوع و معنا |
| --- | --- |
| revision | integer |
| user.id | شناسهٔ کاربر که در Bet.userId هم استفاده می‌شود |
| user.firstName | رشته، حداکثر ۱۰۰ کاراکتر |
| user.lastName | رشته، حداکثر ۱۰۰ کاراکتر؛ در نبود نام خانوادگی "" |
| user.photoUrl | URL عکس تلگرام یا null |

برای کاربر تازه card برابر null است. بعد از ثبت اولیه، کارت می‌تواند pending باشد. برای تغییر کارت تأییدشده، کارت قبلی تا تأیید کارت جدید در card باقی می‌ماند؛ درخواست جایگزین در pendingCard قرار می‌گیرد. پس از تأیید، سرور card را عوض می‌کند و pendingCard و challenge را null می‌کند.

### Challenge

| فیلد | نوع |
| --- | --- |
| id | شناسه |
| method | code یا manual |
| instructions | دستور تأیید مالکیت به صورت متن، حداکثر ۱۵۰۰ کاراکتر |

فرم کد فقط وقتی نمایش داده می‌شود که سرور method برابر code برگرداند. حالت manual فقط وضعیت و دستور سرور را نمایش می‌دهد. رابط هیچ کدی تولید نمی‌کند، هیچ پیام یا انتقالی را خودش معتبر نمی‌شمارد و هیچ endpoint تأییدکننده‌ای در این تحویل ساخته نشده است.

تأیید کارت در پاسخ /api/cards باید متکی به اثبات واقعی از قبل انجام‌شده در سرور باشد؛ صرف ارسال شماره هرگز نباید verified ایجاد کند.

### Round

| فیلد | نوع |
| --- | --- |
| id | شناسه |
| phase | WAITING، FLYING، CRASHED یا ROUND_END |
| model | عدد 0 تا 7، انتخاب سفینه توسط سرور |
| multiplierCents | ضریب فعلی سرور |
| elapsedMs | مدت پرواز 0 تا 86400000 |
| bettingClosesAt | زمان بسته‌شدن ثبت شرط |
| crashCents | فقط پس از پایان دور، برابر ضریب نهایی؛ پیش از پایان null |

در WAITING، ضریب 100 و elapsedMs برابر صفر است. سرور می‌تواند مهلت انتظار را ۵ ثانیه تعیین کند. پس از رسیدن شمارش به صفر، رابط ثبت شرط را می‌بندد، ولی تا دریافت پیام سرور خودش حالت را به پرواز تبدیل نمی‌کند.

در حالت پرواز، مرورگر **هیچ فرمول رشد ضریب یا RNG نتیجه‌ای ندارد**. عدد روی صفحه مستقیماً multiplierCents دریافت‌شده است. زمان محلی صرفاً برای شمارش معکوس و حرکت تزئینی Canvas استفاده می‌شود؛ به تعیین برد یا موجودی راه ندارد.

### HistoryRow

| فیلد | نوع |
| --- | --- |
| id | شناسهٔ دور پایان‌یافته |
| crashCents | ضریب نهایی |
| model | عدد 0 تا 7 |

Proof شامل رشته‌های commitment و serverSeed با حداکثر ۲۵۶ کاراکتر و algorithm با حداکثر ۲۰۰۰ کاراکتر است. این اطلاعات فقط برای دورهای پایان‌یافته نمایش داده می‌شود. نمایش این رشته‌ها به معنی پیاده‌سازی یا تأیید Provably Fair نیست؛ رابط این محدودیت را در پنجره نتیجه ذکر می‌کند. بذر افشاشونده یا ضریب انفجار دور جاری نباید پیش از پایان به مرورگر ارسال شوند.

### Snapshot

| فیلد | نوع |
| --- | --- |
| revision | integer با ترتیب پایدار سمت سرور |
| serverNow | زمان Unix milliseconds هنگام تهیه snapshot |
| round | Round یا null بین دورها |
| bets | آرایهٔ کامل شرط‌های همان دور، حداکثر ۲۰۰۰؛ بدون شناسه یا userId تکراری |

وقتی round برابر null است، bets باید خالی باشد. این قرارداد لیست کامل بازیکنان را دریافت می‌کند؛ برای مقیاس بیش از ۲۰۰۰ بازیکن باید قرارداد صفحه‌بندی و شرط شخصی در آداپتر اضافه شود. در این نسخه snapshot ناقص یا آرایهٔ فراتر از حد پذیرفته نمی‌شود و کنترل‌ها غیرفعال می‌مانند.

سرور باید snapshot کامل را بعد از تغییر وضعیت و هنگام پرواز تقریباً هر ۱۰۰ تا ۲۵۰ میلی‌ثانیه ارسال کند. در تمام مراحل فاصلهٔ ارسال باید کمتر از ۵ ثانیه باشد. revision با تغییر محتوای وضعیت افزایش یابد؛ در heartbeat بدون تغییر، revision ثابت با serverNow تازه مجاز است.

## قرارداد Socket.IO

نسخهٔ ۴ کلاینت Socket.IO از سرور تنظیم‌شده بارگذاری می‌شود. اتصال با auth شامل token برقرار می‌شود. رویدادهای زیر استفاده می‌شوند:

| جهت | رویداد | داده |
| --- | --- | --- |
| سرور ← کلاینت | crash:sync | {}؛ پاسخ acknowledgment باید Snapshot کامل باشد |
| سرور → کلاینت | crash:snapshot | Snapshot کامل |
| سرور → همان کاربر | wallet:updated | Wallet |
| سرور → همان کاربر | profile:updated | Profile |
| سرور → همان کاربر | session:expired | بدون دادهٔ لازم |

در connect_error می‌توان error.data.code برابر AUTH_EXPIRED فرستاد. رویدادهای کیف پول و پروفایل نباید به اتاق عمومی broadcast شوند.

شرط و برداشت با HTTP انجام می‌شوند؛ Socket.IO هیچ فرمان مالی را برای ارسال مجدد پس از قطع ارتباط buffer نمی‌کند. پس از هر اتصال یا بازگشت به تب، snapshot و پروفایل دوباره خوانده می‌شوند. پاسخ با revision قدیمی‌تر اعمال نمی‌شود. نبود heartbeat بیش از ۵ ثانیه کنترل‌ها را غیرفعال می‌کند.

در timeout، خطای شبکه یا پاسخ نامعتبر به عملیات مالی، رابط نتیجه را موفق فرض نمی‌کند. وضعیت «در حال بررسی نتیجه» تا مشاهدهٔ نتیجهٔ معتبر همان عملیات یا عبور به دور بعد حفظ می‌شود. نتیجهٔ یک درخواست دور قبلی نمی‌تواند ثبت شرط در دور جدید را برای همیشه قفل کند.

## مسئولیت بک‌اند آینده

تضمین امنیت مالی فقط با کد فرانت‌اند ممکن نیست. کنترل‌های این فایل برای رفتار صحیح رابط هستند و کاربر قادر به تغییر JavaScript مرورگر است. بک‌اند باید:

- امضای Telegram initData، تاریخ اعتبار و هویت کاربر را بررسی کند.
- مالکیت و یکتایی کارت را با روش واقعی بانک تأیید کند.
- تمام تغییرات کیف پول، ثبت شرط و برداشت را اتمیک، قابل بازیابی و idempotent انجام دهد.
- حداقل مبلغ، موجودی، یک شرط در دور، زمان بسته‌شدن ثبت شرط و مهلت برداشت را مستقل از مرورگر کنترل کند.
- نتیجه و زمان‌بندی مشترک را با RNG امن مدیریت کند و نتیجهٔ آینده را افشا نکند.
- در قطع اتصال، بستن صفحه و ری‌استارت سرویس، شرط و برداشت ثبت‌شده را حفظ کند.
- از ورود مستقیم client به Supabase با service role یا هر secret دیگری جلوگیری کند.

Bot Token، API Hash، Session String، Supabase Service Role Key و رمزهای سرور هیچ جایی در HTML یا تنظیمات عمومی ندارند.

برای تکمیل اتصال در آینده، اطلاعات لازم عبارت‌اند از: URL و قرارداد واقعی API، مسیر و نسخهٔ Socket.IO، روش واقعی تأیید مالکیت کارت، قواعد دقیق شماره کارت، واحد و دقت مبلغ، و قواعد خطا/نسخه‌بندی. این اطلاعات برای مشاهدهٔ فرانت‌اند فعلی لازم نیستند.

## حفظ کد موشک

- تمام مختصات بدنه، بال، پنجره و موتور هشت مدل اصلی حفظ شده‌اند: VANGUARD، ECLIPSE، NOVA، AUREUS، COMET، VIPER، ION و TITAN.
- سحابی، سیارهٔ حلقه‌دار، ماه، ستاره‌ها، شهاب‌ها، دوربین پرواز، شعله، دود، ذرات، موج انفجار و برداشت از کد اصلی منتقل شده‌اند.
- صدای کلیک، شمارش، پرتاب، افزایش سرعت، برداشت، انفجار، موتور و باد با Web Audio حفظ شده‌اند.
- تغییر بال‌ها در wingPolygon انجام می‌شود: رأس‌های اتصال ثابت‌اند و رأس‌های بیرونی نرم خم می‌شوند. بشقاب‌پرنده بالی ندارد.
- منطق محلی تولید دور، برداشت و ذخیره موجودی/آمار حذف شده و تنها تنظیم صدا در localStorage ذخیره می‌شود.
- نمایش نتیجه از سرور جایگزین تاریخچهٔ محلی شده است. دکمه ریست آمار وجود ندارد.
- در کاهش حرکت، تکان دوربین، فلش، ذرات پرتابی و حرکت بال‌ها محدود/حذف می‌شوند. نرخ ترسیم و DPR روی دستگاه ضعیف پایین می‌آیند.

## آزمون‌ها و محدودیت بررسی

    npm ci
    npm test

آزمون‌ها با Node.js و jsdom اجرا می‌شوند. داده‌های آزمایشی **فقط** داخل tests/frontend.test.mjs هستند و فایل HTML هرگز آن‌ها را بارگذاری نمی‌کند.

در بررسی این تحویل، هر ۳۰ آزمون با موفقیت و کد خروج صفر اجرا شدند.

آزمون‌ها اعتبارسنجی، حالت بدون سرور، ناوبری، کپی، ثبات اتصال بال‌ها، بارگذاری هشت سفینه، کارت pending/verified، احراز هویت، رویدادهای موجودی، قطع و وصل، کهنگی snapshot، ارسال یک‌باره، برداشت محفوظ، پاسخ نامشخص، ترتیب snapshot، متن امن بازیکن و آمار دریافتی را پوشش می‌دهند.

Canvas در آزمون DOM با context ثبت‌کنندهٔ فرمان جایگزین می‌شود؛ این آزمون رندر پیکسلی یا آزمون کیفیت بصری نیست. تست روی Telegram واقعی، Android/iPhone، مرورگر واقعی، صدای واقعی و بک‌اند/بانک واقعی در این محیط انجام نشده است. طراحی از 100dvh، visualViewport، Safe Area دستگاه و Telegram، اسکرول مستقل بازیکنان و media query برای صفحه‌های کوتاه استفاده می‌کند؛ بررسی نهایی دستگاه واقعی هنگام اتصال لازم است.
